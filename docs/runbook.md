## First-line health check

When something is wrong, run these first. Most incidents triage from this output alone.

```bash
# Containers up + healthy
docker compose ps

# Mongo is the replica-set primary
docker compose exec mongo mongosh --quiet --eval 'rs.status().myState'   # expect: 1

# RabbitMQ admin UI loads
open http://localhost:15672                       # guest / guest

# Admin dashboard loads (read-only operator view)
open http://localhost:8090

# Each service is listening on its gRPC port
for p in 50051 50052 50053 50054 50055; do
  nc -z localhost $p && echo "OK  $p" || echo "FAIL $p"
done
```

The repo also ships `make status` (backed by `scripts/status.sh`) which bundles many of these probes plus queue depths and outbox lag into one report. Run it first if you have a checkout handy.

## Boot / reset the whole stack

### Fresh boot
```bash
docker compose up --build
```

First boot takes 30-60 s. Healthy state: all services log "listening on :5005X"; `seed` exits 0.

### Stop everything (keep data)
```bash
docker compose stop
```

### Reset everything (drop volumes — destroys all users, payments, ledger)
```bash
docker compose down -v
docker compose up --build
```

After a `-v` reset, the `seed` container will:
- Initialize all Mongo indexes.
- Insert 6 test users (alice, bob, charlie, diana, eve, frank — password `testpass123`).
- Insert 50+ questions from `seed/questions.json`.
- Insert 2 sample tournaments.
- Insert the shop catalog from `seed/shop_items.json`.

### Restart one service
```bash
docker compose restart payment
# or rebuild + restart after a code change
docker compose up --build -d payment
```

> The AMQP channel inside each service does **not** auto-reconnect across RabbitMQ restarts. If you bounce RabbitMQ, restart any service whose logs start showing publish errors.

## Seeding data

The `seed` container runs once at compose-up. Re-run it any time:

```bash
docker compose run --rm seed
```

It's idempotent — Mongo indexes use `ensureIndex` semantics, users are inserted with bcrypt-hashed passwords only if missing, questions upsert by `text`, shop items upsert by `_id`.

### Add a new question
1. Add the entry to `seed/questions.json`.
2. `docker compose run --rm seed`.

### Add a new shop SKU
1. Add to `seed/shop_items.json`.
2. If the SKU is a new `kind`, add the kind constant and validator in `pkg/coins/shop/`.
3. `docker compose run --rm seed`.

### Add a tournament
Two paths:

- **Weekly auto-generated.** The system creates a fresh weekly tournament every Monday (cron in scoring). Index `unique-sparse(autoGenerated, weekKey)` enforces one per week.
- **Manual.** `db.tournaments.insertOne({...})`. Set `startTime`, `endTime`, `requiredPlan` (`"free"` or `"premium"`), `prizePool` array, leave `autoGenerated=false`.

## Inspecting a user

```bash
docker compose exec mongo mongosh quizbattle --quiet --eval '
  const u = db.users.findOne({username:"alice"});
  printjson({
    _id: u._id, username: u.username, plan: u.plan,
    planExpiresAt: u.planExpiresAt, coins: u.coins,
    rating: u.rating, streak: u.streak, winStreak: u.winStreak,
    ownedCosmetics: u.ownedCosmetics,
    equippedCosmeticId: u.equippedCosmeticId,
    rerollCharges: u.rerollCharges,
    streakFreezeHeld: u.streakFreezeHeld
  });
'
```

To list recent ledger entries for a user:

```bash
docker compose exec mongo mongosh quizbattle --quiet --eval '
  const u = db.users.findOne({username:"alice"});
  db.coin_ledger.find({userId:u._id}).sort({createdAt:-1}).limit(20).forEach(r =>
    print(r.createdAt.toISOString(), r.delta, r.reason, r.refId, "(balance after:", r.balanceAfter, ")"));
'
```

If `users.coins` and the ledger sum disagree, that is a bug. The ledger-and-balance pair commits atomically — file an issue with both numbers and the user ID.

## Stuck or zombie matches

Symptoms: a player tells you they're stuck on "loading", the home screen shows a phantom in-progress match, or a room ID lingers in Redis without traffic.

### Inspect Redis state for a room
```bash
docker compose exec redis redis-cli KEYS 'room:<roomId>:*'
# Each key:
docker compose exec redis redis-cli GET   'room:<roomId>:state'
docker compose exec redis redis-cli HGETALL 'room:<roomId>:players'
docker compose exec redis redis-cli GET   'room:<roomId>:round'
docker compose exec redis redis-cli ZRANGE 'room:<roomId>:leaderboard' 0 -1 WITHSCORES
```

All room keys TTL at 30 minutes. A truly stuck room is rare; usually you'll just see a player who hasn't reconnected.

### Force-close a room (last-resort)
```bash
docker compose exec redis redis-cli DEL room:<roomId>:state \
  room:<roomId>:players room:<roomId>:round room:<roomId>:questions \
  room:<roomId>:leaderboard room:<roomId>:match_finalized
```

This won't roll back any side effects already published (e.g., if `match.finished` already fired, the match shows up in history). It just removes the live state. Use only when a client is unreachable and the room is wedged.

### Check who's connected to a room's stream
The quiz service holds streams in an in-process `sync.Map` keyed `"roomId:userId"`. You can correlate room IDs in the quiz service logs:

```bash
docker compose logs --tail=200 quiz | grep <roomId>
```

Expected lines: `room created`, `round 1 started`, `answer received`, `round closed`, `match finalized`.

### Re-pair a player whose subscribe stream dropped
Players who fall out of `MatchmakingService.SubscribeToMatch` mid-pairing just re-tap **Play** in the app. The quota was already debited but the daily-quota refund on `LeaveMatchmaking` covers this when the client knows to call it. If they don't, the user effectively pays one quiz of their daily quota — acceptable in v1.

## Payments: replay, refund, debug

### Replay a webhook locally
Razorpay sends webhooks to a public URL. In dev, use ngrok (or `cloudflared`) and configure the Razorpay dashboard webhook to `https://<tunnel>/webhook/razorpay`. Alternatively, exercise the same code path via gRPC:

```bash
grpcurl -plaintext -H "authorization: Bearer <jwt>" \
  -d '{"razorpay_order_id":"order_xxx","razorpay_payment_id":"pay_xxx","razorpay_signature":"<hmac>"}' \
  localhost:50055 quiz.PaymentService/VerifyPayment
```

The signature is HMAC-SHA256(`RAZORPAY_KEY_SECRET`, `order_id + "|" + payment_id`). Razorpay test mode produces real signatures; we don't fake them in dev.

### Re-fire a webhook by hand (debug only)
Build a body matching Razorpay's `payment.captured` shape, sign it with `RAZORPAY_WEBHOOK_SECRET`:

```bash
BODY='{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_xxx","order_id":"order_xxx","amount":29900,"currency":"INR","status":"captured"}}}}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$RAZORPAY_WEBHOOK_SECRET" -hex | sed 's/^.* //')
curl -X POST http://localhost:8080/webhook/razorpay \
  -H "X-Razorpay-Signature: $SIG" -H "Content-Type: application/json" \
  --data "$BODY"
```

A second identical request is a no-op (SETNX idempotency).

### Inspect a user's plan history
```bash
docker compose exec mongo mongosh quizbattle --quiet --eval '
  db.payments.find({userId:"<userId>"}).sort({createdAt:-1}).forEach(printjson);
'
```

### "User says their plan never upgraded"

1. Find the `payments` row by `razorpayOrderId` (the user can read it from the Razorpay receipt or in-app payment history).
2. Check `status`. If it's still `"created"`, the capture path didn't run.
3. Check the `webhook:idempotency:<paymentId>` Redis key. If present, capture *did* run — look at `users.{userId}.plan` and `planExpiresAt`. If those are correct, the user's app needs to call `GetPlanStatus` again or restart.
4. If neither path ran, ask the user to retry payment from the in-app **Try again** dialog (it reuses the same Razorpay order so no duplicate row is created).

### Refunds
Refunds are out of scope of the backend — they happen on the Razorpay dashboard. After a refund, manually set the user's plan back to `"free"` and zero `planExpiresAt`:

```bash
docker compose exec mongo mongosh quizbattle --quiet --eval '
  db.users.updateOne({_id:"<userId>"}, {
    $set: {plan:"free", planExpiresAt: 0},
    $unset: {premiumExpiryWarned: ""}
  });
'
docker compose exec redis redis-cli DEL user:<userId>:plan
```

## Coins: balance vs ledger, granting manually

### Balance/ledger sanity check
```bash
docker compose exec mongo mongosh quizbattle --quiet --eval '
  const u = db.users.findOne({username:"alice"});
  const sum = db.coin_ledger.aggregate([
    {$match: {userId: u._id}},
    {$group: {_id: null, sum: {$sum: "$delta"}}}
  ]).toArray()[0].sum;
  print("users.coins =", u.coins, " ledger sum =", sum, " match? =", u.coins === sum);
'
```

They must match. If they don't, [adr-0005](./decisions/0005-coin-ledger-transactional.md)'s invariant is broken — file a bug.

### Grant coins manually (e.g., support credit)
Do **not** `db.coin_ledger.insertOne(...)` directly. The ledger insert and `users.coins $inc` must commit together. Use a small admin script that calls `coins.Grant`:

```go
package main

import (
    "context"
    "log"
    "os"

    "go.mongodb.org/mongo-driver/v2/mongo"
    "go.mongodb.org/mongo-driver/v2/mongo/options"

    "quiz-battle/pkg/coins"
)

func main() {
    uri := os.Getenv("MONGO_URI")
    c, err := mongo.Connect(options.Client().ApplyURI(uri))
    if err != nil { log.Fatal(err) }

    l := coins.NewLedger(c, coins.DefaultDBName)
    entry, err := l.Grant(context.Background(), "<userId>", 500,
        coins.ReasonAdminAdjustment, "admin:ticket-1234:<userId>",
        map[string]string{"reason": "support credit"})
    if err != nil { log.Fatal(err) }
    log.Printf("granted: %+v", entry)
}
```

The `refId` (`admin:ticket-1234:<userId>`) makes the grant idempotent — re-running the script with the same `refId` is a no-op.

### Stuck premium-trial outbox rows

Symptom: a user bought a 3-day trial but their plan isn't extended after a few seconds.

```bash
docker compose exec mongo mongosh quizbattle --quiet --eval '
  db.coin_effect_outbox.find({processedAt:null}).forEach(printjson);
'
```

Healthy: empty. Anything older than ~5 s means the payment service consumer is wedged.

Common causes:
- **Mongo unreachable.** The whole stack is degraded; fix Mongo.
- **User document missing for `userId`.** The consumer logs and marks the row processed; should be self-healing.
- **Bug in `applyPremiumTrialRow`.** Check `docker compose logs payment | grep premium-trial`.

Manual fix: restart the payment service. Do not edit the row's `processedAt` — the consumer's renewal-aware logic depends on the row being unprocessed when it runs.

## Notifications: drop reasons, stub mode, FCM setup

### Find out why a push didn't arrive
```bash
docker compose logs notification | grep -E 'sent|dropped' | grep <userId>
```

Look for lines like `dispatch dropped reason=quiet_hours category=streak.warning userId=...`. The five drop reasons are: `muted` (user opt-out), `quiet_hours`, `daily_cap`, `dedup`, `firebase_error`.

### Stub mode
If `secrets/firebase-admin.json` is absent or invalid, the notification service runs in stub mode: it logs every dispatch instead of sending an FCM push. Policy gate and counters still execute. You can run the whole stack end-to-end without ever configuring Firebase.

### Enabling real pushes
1. Firebase Console → Project Settings → Service accounts → Generate new private key.
2. Save the file as `secrets/firebase-admin.json`.
3. `docker compose restart notification`.
4. Send a test push via the streak-warning cron — or trigger any RabbitMQ `notif.*` event manually:

```bash
docker compose exec rabbitmq rabbitmqadmin publish \
  exchange=sx routing_key=notif.streak.warning \
  payload='{"userId":"<userId>","currentStreak":2,"event":"notif.streak.warning"}'
```

## Tournaments

### Force-finalize a tournament (testing)
The finalization worker runs every 60 s and looks for `status:"completed"` rows with `winnersAwarded:{$ne: true}`. To make a tournament eligible immediately:

```bash
docker compose exec mongo mongosh quizbattle --quiet --eval '
  db.tournaments.updateOne(
    {_id: "<tournamentId>"},
    {$set: {endTime: new Date(Date.now()-1000), status: "completed"}}
  );
'
```

Within 60 s, the worker picks it up, computes top-N from `tournament_standings`, writes `tournament_payouts` rows, publishes `coins.earn.tournament_placement` per winner. The earn consumer grants the coins.

### Check tournament standings
```bash
docker compose exec mongo mongosh quizbattle --quiet --eval '
  db.tournament_standings.find({tournamentId:"<tournamentId>"}).sort({score:-1}).forEach(printjson);
'
```

## RabbitMQ: queues, DLQs, redrive

### Inspect queues
Open `http://localhost:15672` (guest / guest). Useful columns: queue name, ready (pending), unacked, deliveries per second.

Healthy steady-state: every queue has 0 ready and 0 unacked. A growing `ready` count means a consumer is down or behind.

### DLQs to watch
- `coin-earn-dlq` — bad earn payloads. If non-empty, the producer is misbehaving; redrive only after fixing the producer.
- `referral-event-dlq` — bad referral events.
- `notif-dlq` (if configured) — pushes that failed all FCM retries.

### Redrive a DLQ
On the RabbitMQ admin UI, **Queues → DLQ → Get messages → Get message(s)** to inspect. To replay, use **Move messages** to the live queue (or write a tiny consumer that does the same).

```bash
docker compose exec rabbitmq rabbitmqadmin get queue=coin-earn-dlq ackmode=ack_requeue_false
# inspect, then re-publish manually after fixing the producer:
docker compose exec rabbitmq rabbitmqadmin publish \
  exchange=sx routing_key=coins.earn.match_win \
  payload='{"userId":"<id>","amount":100,"refId":"match:<roomId>:user:<id>"}'
```

### Reset a consumer queue (last resort)
```bash
docker compose exec rabbitmq rabbitmqctl purge_queue coin-earn-queue
```

Purge is destructive — any unacked messages are lost. Use only when the queue is full of confirmed garbage.

## Rotating secrets

### `JWT_SECRET`
Every service must share the same secret. Rotation procedure (zero-downtime impossible without two-secret support, which we don't have today):

1. Pick a new secret: `openssl rand -hex 32`.
2. Update `.env` (`JWT_SECRET=<new>`).
3. `docker compose up -d --no-deps --build auth matchmaking quiz scoring payment notification admin`.
4. **All existing access tokens become invalid.** Clients silently re-issue via refresh token, which is opaque and stored server-side — refresh continues to work, the refresh response carries a fresh JWT signed with the new secret.

So in practice: rotate JWT, *do not* purge the refresh store, and clients re-link to new access tokens transparently.

### `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET`
1. Generate a new key pair in the Razorpay dashboard.
2. Update `.env`.
3. `docker compose up -d --no-deps --build payment`.
4. Any in-flight Razorpay orders created with the old key are still capturable — Razorpay validates by order ID, not by which key was last seen. New orders use the new key.

### `RAZORPAY_WEBHOOK_SECRET`
Set the new secret in the Razorpay dashboard webhook config first, then update `.env`, then restart payment. If you flip the order, a webhook in flight may fail HMAC. Razorpay re-delivers, so it self-heals — but the cleaner order avoids the noise.

### `RESEND_API_KEY`
1. Generate a new key on resend.com.
2. Update `.env`.
3. `docker compose up -d --no-deps --build auth`.

### `GOOGLE_CLIENT_ID`
Rotating the client ID requires re-issuing the OAuth credentials in Google Cloud Console. Coordinate with the Flutter team — the Flutter side has the matching `GOOGLE_CLIENT_ID` baked into `flutter/lib/services/auth_service.dart` (or read from `--dart-define`).

### Firebase service account
1. Rotate in Firebase Console → Service accounts → Generate new private key.
2. Replace `secrets/firebase-admin.json`.
3. `docker compose restart notification`.

## Metrics + alerts (suggested)

The repo doesn't ship a Prometheus / Alertmanager stack — `:2112/metrics` is exposed per service, ready to scrape. Suggested alerts when you stand one up:

| Alert | Expression | Burn-in |
|---|---|---|
| Payment outbox stuck | `outbox_oldest_age_seconds{kind="premium_trial"} > 600` | 5 m |
| RabbitMQ queue depth | `rabbitmq_queue_messages_ready > 50` per queue | 5 m |
| FCM delivery failure rate | `rate(notif_dispatch_total{result="error"}[5m]) > 0.1 × rate(notif_dispatch_total[5m])` | 10 m |
| Mongo replica health | `mongodb_member_state != 1` | 1 m |
| gRPC error rate | `rate(grpc_request_duration_seconds_count{code!="OK"}[5m]) > 0.05 × rate(...[5m])` | 5 m |
| AMQP publish failure | `rate(amqp_publishes_total{status="err"}[5m]) > 0` | 5 m |

Until then, the admin dashboard at `:8090` and `make status` are the lightweight equivalents.

## Common error patterns and fixes

| Symptom | First thing to check |
|---|---|
| Flutter shows "stream closed" mid-match | Quiz service logs around the room ID; usually network or service restart |
| Daily quota counter says "0 remaining" but user only played twice | Inspect `user:{id}:daily_quota` TTL; if midnight rolled in user's TZ, the key should have expired. If not, the EXPIREAT was missed — `DEL` the key to reset |
| User says "I claimed daily reward twice today" | Look at `users.<id>.rewardClaimedDate`. If today, the `$ne: today` filter should have prevented the second claim — this is a bug, file it |
| RabbitMQ shows growing `ready` on `coin-earn-queue` | scoring service is wedged or paused; check `docker compose logs scoring` |
| Payment service log: "razorpay HTTP timeout" | Razorpay endpoint slow; the 10 s timeout caps the impact. Retry the order from the app |
| Notification service log: "firebase auth failed" | `secrets/firebase-admin.json` is missing/expired/invalid. Re-mint and replace |
| `coin_effect_outbox` rows older than 30 s | premium-trial consumer wedged; restart payment |
| Mongo errors: "Transaction numbers are only allowed on..." | `?replicaSet=rs0` missing from MONGO_URI — check env vars on the affected service |
| Two players matched but the round never starts | Check `match.created` was published (RabbitMQ Activity Log) and consumed by quiz (quiz log); if both fine, the question selection failed — Mongo `questions` collection may be empty (re-seed) |

For anything not on this list, the playbook is the same: `docker compose logs <service>` for the timeframe, RabbitMQ admin UI for queue depth, Mongo + Redis for state, and the admin dashboard at `:8090` for a system-wide read-only snapshot.
