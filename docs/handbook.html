The Product

Quiz Battle is a real-time 1v1 multiplayer quiz game. Two strangers (or two friends) get matched, a server-driven game loop streams ~10 questions at them, fastest correct answer wins points each round, and at the end somebody walks away with a higher Elo rating and a pile of in-game coins.

What features exist

  • Auth — username/password, guest login, Google Sign-In, email-OTP login, password reset.
  • Real-time matches — rating-based matchmaking, server-streamed questions, live leaderboard updates between answers, timer sync.
  • Coin economy — earn coins from match wins, daily-reward streaks, referral conversions; spend them in a shop for cosmetics, streak-freeze items, premium trials, re-rolls.
  • Premium subscriptions — paid via Razorpay (UPI/cards/netbanking, India), 30 days, renewal-aware.
  • Referrals — unique codes, dashboard, rewards on first match of the invited friend.
  • Streaks & daily rewards — claim once per day, freeze items bridge one missed day.
  • Tournaments & global leaderboard — points-based ranking, weekly prize payouts.
  • Push notifications — FCM-routed events for streaks, rewards, friend requests, challenges, premium expiry.
  • Friends & challenges — add by username or referral code, presence (online/offline), direct 1v1 challenge (covered in detail at the end).
  • Analytics — per-topic accuracy, response-time percentiles, 30-day rating chart, monthly recap.

Why six services and not one

Each service can be deployed, scaled, and crashed independently. If the payment service has a bug, matches still play. If a tournament cron explodes, login still works. Splitting on bounded contexts (auth, money, real-time gameplay) is also a hiring-friendly mirror of how big teams actually divide work.

Tech Stack — Every Tool Explained

Go (Golang) backend language

What it is: A statically typed compiled language from Google. Designed for servers — fast startup, low memory, native concurrency via goroutines and channels.

Why here: Real-time games punish latency. Go's goroutines let one process hold thousands of long-lived gRPC streams cheaply (~2 KB per goroutine stack), and a single static binary deploys in a 20 MB Alpine container. Strong typing catches whole categories of bugs before runtime — important when money (Razorpay, coins) flows through.

How used: Every backend service is a Go main.go that boots a gRPC server, opens connections to Mongo/Redis/Rabbit, registers handlers, and blocks on lifecycle.WaitForSignal until SIGTERM.

Fresher note

A goroutine is a lightweight thread managed by Go's runtime, not the OS. You spawn one with go someFunc(). Channels (chan T) are typed pipes you send values through — the Go-idiomatic way to coordinate goroutines without manual locking.

gRPC + Protobuf communication protocol

What they are: Protobuf (Protocol Buffers) is a schema language and binary serialization format. You define your API in a .proto file, then a code generator produces typed client + server stubs in any language. gRPC is the RPC framework built on Protobuf + HTTP/2.

Why here: One proto/quiz.proto file is the single source of truth — both Go services and the Flutter client generate from it. No risk of the client and server disagreeing about field names. HTTP/2 multiplexing lets one TCP connection carry many concurrent calls, and gRPC server streaming is the cheapest way to push real-time game events at the client.

How used: 5 services expose gRPC servers, Flutter dials them. Two RPCs are server-streaming:

  • SubscribeToMatch — Flutter calls it, the matchmaking server holds the stream open and pushes one MatchEvent when the player is paired.
  • StreamGameEvents — during a match, the quiz server pushes a oneof union (QuestionBroadcast, LeaderboardUpdate, RoundResult, MatchEnd, TimerSync).
// excerpt from proto/quiz.proto
message GameEvent {
  uint64 sequence_number = 1;
  oneof event {
    QuestionBroadcast  question     = 2;
    LeaderboardUpdate  leaderboard  = 3;
    RoundResult        round_result = 4;
    MatchEnd           match_end    = 5;
    PlayerJoined       player_joined= 6;
    TimerSync          timer_sync   = 7;
  }
}
Why oneof

Different events have different shapes, but they all flow over the same stream. oneof lets us define them as one union type — the receiver checks which field is set and handles accordingly. It's the typed alternative to "type: 'leaderboard' + a string-keyed map".

Flutter + Dart client

What it is: Google's UI toolkit. Write once in Dart, compile to native Android, iOS, web, macOS, Linux, Windows. Renders its own widgets via Skia/Impeller (not native controls), so pixel-perfect identical UI everywhere.

Why here: One team, one codebase, two app stores. Hot reload makes UI iteration fast. Strong gRPC support via the grpc Dart package.

How used: flutter/lib/ contains 21 screens, 7 service wrappers, 4 Riverpod state providers, generated proto stubs, and a dark Material 3 theme.

MongoDB primary database

What it is: A document database. Instead of tables/rows, you store JSON-like documents in collections. Each document can have any fields; you index the ones you query.

Why here: User profiles evolve fast in early-stage products (new fields every PR: streak, preferred_topics, fcmToken, planExpiresAt, onboarding_completed, …). A schema-less store means we add fields without migrations. Sparse unique indexes let optional fields (email, googleId, referralCode) be unique when set.

How used: Collections include users, questions, answer_log, rating_history, friend_requests, coin_ledger, coin_effect_outbox, payments, tournaments, shop_items, shop_inventory.

Gotcha — replica set

Mongo runs as a single-node replica set (rs0) in our docker-compose, not standalone. Why? Multi-document transactions (used in pkg/coins/ledger.go for atomic ledger writes) require a replica set. The compose healthcheck idempotently runs rs.initiate() on first boot.

Redis in-memory state

What it is: An in-memory key-value store with rich data structures (strings, hashes, sets, sorted sets, streams) and atomic Lua scripting. Sub-millisecond reads/writes.

Why here: Real-time gameplay can't take a 10ms Mongo round-trip per answer. Redis stores everything that's "live": the matchmaking pool, room state, the leaderboard for an in-progress match, the daily-quota counter, presence flags, idempotency keys.

Key patterns used:

  • ZADD / ZRANGEBYSCORE — matchmaking pool sorted by rating, leaderboard sorted by score.
  • SETNX (set if not exists) — idempotency guards (payment verify, friend challenge throttle, referral code generation).
  • HSET / HGETALL — room player hashes (room:{id}:players).
  • INCR + EXPIRE — rate-limit windows (login, answer-submit, referral-apply).
  • EVALSHA — Lua script for atomic leaderboard read-modify-write.
  • PEXPIRE — presence TTL (presence:{userId}, refreshed by Heartbeat RPC).

RabbitMQ message broker

What it is: A message broker that routes events between producers and consumers, with durable queues and acknowledgements (so messages survive crashes).

Why here: When the quiz service finishes a match, the scoring service needs to persist it, the notification service needs to push a "you won" FCM, and the analytics service needs to update a leaderboard — all without the quiz service waiting for any of them. RabbitMQ decouples publishers from subscribers. If the notification service crashes, the message waits in the queue and is delivered when it restarts.

How used: One topic exchange (sx) carries everything. Services bind queues to routing-key patterns:

  • match.created — published by matchmaking, consumed by quiz to start a room.
  • match.finished — published by quiz, consumed by scoring to persist + grant coins.
  • coin.earn.* — internal earn events (referral, match win) routed to pkg/coins ledger consumer.
  • notif.* — every push notification (notif.friend.challenge, notif.streak.warning, notif.premium.expired, …) consumed only by the notification service.
Why RabbitMQ over Kafka

(See docs/decisions/0004-rabbitmq-over-kafka.md.) We need per-message routing based on event types, not high-throughput log streaming. Kafka shines for "millions of events/sec into a few topics"; RabbitMQ shines for "dozens of routing keys, ack/nack semantics, manageable UI". For a quiz app at our scale, Rabbit's operational simplicity wins.

JWT (HS256) auth tokens

What it is: A JSON Web Token is a self-contained signed credential. Three base64 parts separated by dots: header.payload.signature. The signature proves the server issued it; the payload carries claims like userId and exp.

Why here: Stateless. The server doesn't keep a session table in Redis — it just verifies the HMAC-SHA256 signature on each request. Faster per-RPC, easier to scale horizontally (no shared session store).

How used: Auth service issues a token on login (24h expiry). Every other service runs a gRPC interceptor (pkg/auth.UnaryInterceptor / StreamInterceptor) that extracts Authorization: Bearer <token> from gRPC metadata, verifies it, and stuffs the user ID into the request context.

// pkg/auth/middleware.go (sketch)
func UnaryInterceptor(secret string) grpc.UnaryServerInterceptor {
  return func(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
    if isPublic(info.FullMethod) {           // Login, Register, etc.
      return handler(ctx, req)
    }
    token := extractBearer(ctx)               // from metadata
    claims, err := jwt.Parse(token, secret)   // HMAC verify
    if err != nil { return nil, status.Error(codes.Unauthenticated, "bad token") }
    ctx = context.WithValue(ctx, userIDKey{}, claims.UserID)
    return handler(ctx, req)
  }
}
Why HS256, not RS256

HS256 uses one shared secret (JWT_SECRET). RS256 uses a public/private key pair — better when the issuer and verifier are different organizations. Here all services are ours and run together, so HS256 is simpler. We do enforce the algorithm explicitly when parsing to prevent the classic alg:none attack.

Razorpay payments

What it is: An Indian payment gateway. UPI, cards, netbanking, wallets — all behind one API. Test mode for development with dummy cards.

Why here: The product targets India, where UPI dominates. Razorpay's Flutter SDK opens a native checkout sheet; on completion it returns a payment ID + signature, which our backend verifies.

How used: Two-stage flow:

  1. CreateOrder RPC → our payment service calls Razorpay's Orders API server-side, returns the order ID to Flutter.
  2. Flutter opens Razorpay Checkout with that order ID. On success, Razorpay returns (paymentId, orderId, signature) to the app.
  3. VerifyPayment RPC → backend HMAC-verifies the signature (HMAC_SHA256(orderId + "|" + paymentId, secret)), upgrades the user's plan.
  4. An HTTP /webhook endpoint (port 8080) serves as a backup: Razorpay calls it server-to-server when a payment captures, in case the app crashed before VerifyPayment. Webhook also HMAC-verifies and is idempotent via Redis SETNX on paymentId.
Why both VerifyPayment and webhook

VerifyPayment is fast (user gets premium instantly). The webhook is a safety net (if the app died after payment but before VerifyPayment fired). Idempotency via SETNX ensures we don't upgrade the user twice.

Firebase Cloud Messaging (FCM) push notifications

What it is: Google's free push-notification service. You upload a service-account JSON, get an SDK, send a payload to a device token, and the user's phone wakes up and shows a notification.

Why here: Free, multi-platform (Android + iOS), reliable. We need to wake up the app for friend challenges, daily-reward reminders, streak warnings, premium expiry.

How used: The notification service is the only service that talks to FCM. Other services publish notif.* events to RabbitMQ; the notification service consumes them, runs them through a policy gate (quiet hours, daily cap, dedup, user mutes), looks up the user's fcmToken in Mongo, and sends via Firebase Admin SDK.

Stub mode: if secrets/firebase-admin.json is missing, the service logs notifications instead of sending them — perfect for local dev without a real Firebase project.

Docker + Docker Compose infrastructure

What they are: Docker packages an app + its dependencies into an immutable image; Compose runs many containers together as one declarative stack.

Why here: One docker compose up brings up 9 containers (Redis, RabbitMQ, Mongo, seed, 6 services). New contributors don't have to install Go, install Mongo, install Redis individually. Reproducible local dev.

How used: A multi-stage Dockerfile compiles all 6 services + the seed binary in one Go builder image, then copies binaries into a tiny Alpine runtime (~20 MB final). docker-compose.yml wires depends_on + healthchecks so services start in order (Mongo healthy → seed runs → services boot).

Why here: Compile-safe dependency injection (no string keys), automatic disposal when nothing watches a provider anymore, first-class support for async data (FutureProvider, StreamProvider) — perfect for gRPC calls.

Prometheus metrics + slog observability

What they are: Prometheus is a time-series metrics system — services expose a /metrics endpoint serving counters/histograms; a Prometheus server scrapes them. slog is Go's standard structured-logging package — every log line is a JSON object with consistent fields.

Why here: When something goes wrong in production, you need numbers (P99 latency, error rate, queue depth) and you need logs that filter by user/request ID. Structured logs are greppable and machine-parsable.

How used:

  • Every service starts a metrics server on port 2112 (host-mapped to 21251–21256). pkg/metrics defines counters (RecordPublish, RecordDispatched, RecordConsume) used at every Rabbit publish/consume site.
  • Every service initializes pkg/log on boot, which configures slog with JSON output, log-level from LOG_LEVEL env, service name in every record.
  • gRPC interceptors (pkg/log.UnaryServerInterceptor) log every RPC start/finish with method, latency, error code, user ID — and propagate a request_id through the context.
  • The request ID is carried over AMQP too (in message headers), so a single match-finished event can be traced from quiz → scoring → notification in one log query.

How the referral code is generated (the user's example)

Lives in services/auth/main.go:828.

func generateReferralCode() string {
    b := make([]byte, 4)              // 4 random bytes from crypto/rand
    rand.Read(b)                      // = 32 bits of entropy
    return "REF" + strings.ToUpper(hex.EncodeToString(b))
    //     ^^^^      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //     prefix    8 uppercase hex chars
}
// Example output: "REFA3B91F2C"

Then generateUniqueReferralCode wraps it in a collision-safe loop using Redis SETNX:

func (s *authServer) generateUniqueReferralCode(ctx, userID string) string {
    for i := 0; i < 5; i++ {
        code := generateReferralCode()
        ok, err := s.rdb.SetNX(ctx, keys.RefCode(code), userID, 0).Result()
        //                                              ^^^^^^^^^   ^
        //                                              userID      no TTL — codes live forever
        if err == nil && ok { return code }   // SETNX returned true: we own this code
    }
    // 5 collisions in a row is statistically impossible with 32-bit entropy
    // unless Redis is broken — fall back to a force-set on the 6th attempt.
    code := generateReferralCode()
    keys.SetRefCode(ctx, s.rdb, code, userID)
    return code
}
Why this algorithm

Why crypto/rand? Predictable codes would let attackers guess them. Why hex, not base32/base64? Hex is the most copy-paste-friendly for users typing it manually — no ambiguous chars (no O/0 or l/I/1). Why 32 bits? 4 billion possible codes — collisions are ~1 in 2 billion at our user counts. Why SETNX instead of just inserting? Race-safe: two simultaneous signups generating the same code (vanishingly unlikely but possible) won't both succeed. Why prefix "REF"? So a user pasting "ABC123" into the referral field obviously sees their mistake — and so we can later expand to "TRN" for tournament-specific codes without ambiguity.

The Redis key is refcode:<CODE> → userID. Reverse-lookup ("which user owns REFA3B91F2C?") is one GET.

On success, extract: sub (Google's stable user ID), email, name, picture. Upsert:

The empty-GOOGLE_CLIENT_ID security hole

If s.googleClientID is empty string, idtoken.Validate skips the audience check entirely. That means any valid Google ID token — issued for any other app on the planet — would pass verification. An attacker with a Google account could obtain a token for some other public OAuth client and use it to log in as anyone. config.MustRequired(ctx, "GOOGLE_CLIENT_ID") at startup (line 1090) is the guardrail. For local dev, set it to anything non-empty (e.g. dev-disabled.apps.googleusercontent.com) — Google tokens will then fail audience verification, which is exactly what you want when you're not actually testing Google Sign-In.

Email OTP — generating a 6-digit code

func generateCode() string {
    b := make([]byte, 3)                           // 3 random bytes = 24 bits
    rand.Read(b)
    n := (int(b[0])<<16 | int(b[1])<<8 | int(b[2])) % 1000000
    //   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //   pack into one int, mod by a million

Matchmaking — services/matchmaking/main.go

port 50051~602 lines Pair players, create rooms.

The pool — a single sorted set

One Redis key, matchmaking:pool, holds every waiting player across the whole game. It's a sorted set (ZSET) — score = rating, member = userID.

// pkg/keys/redis.go:32
func AddToPool(ctx context.Context, rdb *redis.Client, userID string, rating float64) error {
    return rdb.ZAdd(ctx, MatchmakingPool, redis.Z{Score: rating, Member: userID}).Err()
}

Why sorted by rating: it makes finding "two players near each other" a ZRANGE by index, which Redis does in O(log N + M).

JoinMatchmaking — the gate chain

  1. Auth — JWT verified by middleware (interceptor), userID already in context.
  2. Daily quota check (keys.CheckQuota) via a Lua script: 
    local current = redis.call('INCR', KEYS[1])
redis.call('EXPIREAT', KEYS[1], tonumber(ARGV[2]))
if current > tonumber(ARGV[1]) then
  redis.call('DECR', KEYS[1])    -- ⬅ roll back the INCR; this attempt didn't count
  return 0                        --     0 = denied
end
return 1                          --     1 = allowed
    The key is user:<userID>:daily_quota. The expire is set to IST midnight (so it resets at 00:00:00 IST, not 24h after first call). Free plan: limit = 1. Premium: skipped entirely upstream.

    Why DECR on rejection? So a user denied at attempt 2 doesn't have their counter sitting at 2 — if their plan upgrades mid-day, they should be able to play immediately, not "play one more from now". Lua makes the INCR/DECR pair atomic so two simultaneous calls can't both succeed.
  3. Duplicate-presence check — ZSCORE matchmaking:pool <userID> returns nil if the user isn't in the pool. If they are, return early (idempotent JoinMatchmaking).
  4. ZADD them into the pool with their current rating.
  5. Return immediately — pairing happens out-of-band in the pairer goroutine; the client's SubscribeToMatch stream is what learns about the result.

The pairer goroutine

One ticker, fires every 500 ms:

func (s *matchmakingServer) tryCreateRoom(ctx context.Context) {
    poolSize, _ := keys.PoolSize(ctx, s.rdb)
    if poolSize < 2 { return }                    // not enough players, skip tick
    count := poolSize
    if count > 10 { count = 10 }                  // cap batch at 10 to keep ticks cheap
    players, _ := keys.PopPoolPlayers(ctx, s.rdb, count)
    s.createRoom(ctx, players)
}

How PopPoolPlayers stays atomic: it's a Lua script that does ZRANGE 0 N-1 followed by ZREMRANGEBYRANK 0 N-1 in one shot — two ticks can't both pop the same user. The script returns the popped userIDs.

Pairing strategy: The popped list is already sorted by rating (lowest first since ZSET defaults). The current implementation pairs them sequentially as (players[0], players[1]), (players[2], players[3]), etc. — i.e. closest-rating neighbors. There's no explicit "rating tolerance window" — the assumption is that if you've been in the pool long enough to be popped, any opponent is better than waiting more.

Creating a room

For each pair, createRoom:

  1. Generates a UUID room ID.
  2. Writes room:<id>:players (hash: userID → "joined"), room:<id>:state (JSON: {status: "waiting", round: 0, ...}), room:<id>:round (string: "0") to Redis via TxPipeline (one MULTI/EXEC).
  3. Increments an atomic seqCounter for the MatchEvent sequence number (used by clients to detect dropped events).
  4. Builds the MatchEvent:

    "roomId":    roomID,

}

SubscribeToMatch — the in-memory subscriber registry

// On stream open:
ch := make(chan *pb.MatchEvent, 10)                    // 10-event buffer per subscriber
if old, loaded := s.subscribers.LoadAndDelete(userID); loaded {
    close(old.(chan *pb.MatchEvent))                   // kick off any stale stream
}
s.subscribers.Store(userID, ch)                        // sync.Map[userID]chan
for {
    select {
    case event, ok := <-ch:
        if !ok { return nil }                          // channel closed → stream ends
        if err := stream.Send(event); err != nil { return err }
    case <-stream.Context().Done():
        return stream.Context().Err()                  // client disconnected
    }
}

Why sync.Map? Go's regular map needs a mutex on every read/write. sync.Map is optimized for "write-once, read-many" patterns. Each user updates their entry rarely (only on stream open/close) but the pairer reads many entries every 500ms.

What if a user has two devices connected? LoadAndDelete + close(old) kicks the previous stream — the most recent subscribe wins. The kicked client sees its stream end and re-subscribes via Flutter's retry logic.

What if the buffer fills up? Push is non-blocking via select { case ch <- e: default: } — events to a slow client are dropped. In practice the buffer is 10 events deep and a user only ever receives one MatchEvent per JoinMatchmaking, so this never trips.

Why this needs to be Lua and not just Go code

Imagine both players answer at exactly the same millisecond. In a naive Go implementation:
(1) goroutine A reads "Alice = 100"
(2) goroutine B reads "Alice = 100" (still 100 — A hasn't written yet)
(3) A writes "Alice = 250" (added 150)
(4) B writes "Alice = 220" (added 120, based on stale read) — A's update is gone.
Redis runs Lua scripts as a single command. No other client can interleave. The read-modify-write becomes one atomic step.

func (s *scoringServer) drainChallengeNotifOnce(ctx context.Context) {
    cur, _ := s.mongoDB.Collection("friend_challenge_outbox").Find(ctx,
        bson.M{"processedAt": nil},                       // only un-published rows
        options.Find().
            SetLimit(200).
            SetSort(bson.D{{Key: "createdAt", Value: 1}}), // oldest first
    )
    for cur.Next(ctx) {
        var row challengeNotifOutboxRow
        cur.Decode(&row)
        s.republishChallengeNotif(ctx, row)               // publish + mark processed
    }
}

Why a startup pass before the ticker? If the service crashed mid-publish 10 seconds ago, you don't want to wait another 30s for the first tick. A user just sent a challenge and is staring at the friend's "should I have heard a notification?" face — boot-time drain catches that.

On publish failure: bump attempts counter (so an operator can spot rows stuck in a doom loop), leave processedAt = nil, the next tick retries.

On publish success: set processedAt = now. Future passes skip this row.

Duplicate sends: If we crash between publish-success and mark-processed, the next pass republishes the same notif. The notification service is idempotent on (recipientId, roomId) with a 5-min dedup window — so the worst case is a single duplicate FCM, which is "your phone buzzes twice." Acceptable.

VerifyPayment — HMAC signature in detail

When Razorpay Checkout completes, the SDK returns (razorpay_payment_id, razorpay_order_id, razorpay_signature) to Flutter. Flutter forwards all three to our backend. The backend verifies:

mac := hmac.New(sha256.New, []byte(s.razorpaySecret))
mac.Write([]byte(req.RazorpayOrderId + "|" + req.RazorpayPaymentId))
//                                    ^^^
//                                    literal pipe character
expected := hex.EncodeToString(mac.Sum(nil))

if !hmac.Equal([]byte(expected), []byte(req.RazorpaySignature)) {
    return nil, status.Error(codes.PermissionDenied, "invalid payment signature")
}

Why HMAC-SHA256? It proves the message came from someone holding the secret without revealing the secret. Razorpay generates the signature server-side using the same secret we hold; if our recomputed signature matches, we know Razorpay (not an attacker) issued it.

Why hmac.Equal instead of ==? Timing-safe comparison. Naive byte-by-byte equality returns early on the first differing byte, leaking how many leading bytes matched — a timing oracle for forging signatures. hmac.Equal always compares all bytes.

Why the pipe? Razorpay's spec. Prevents orderId="A"+paymentId="BC" from colliding with orderId="AB"+paymentId="C" (both would concatenate to "ABC" without a separator).

Why the whole thing runs in a Mongo transaction:

session.WithTransaction(ctx, func(sc context.Context) (any, error) {
    // 1. Re-read user inside the session (consistent snapshot).
    // 2. Compute new expiry from that snapshot.
    // 3. UpdateOne(users) to set plan + planExpiresAt.
    // 4. MarkProcessed(outbox row) — flips processedAt.
    // All four either commit together, or none commit.
})

Why is this critical? Without the transaction, this race exists:

  1. UpdateOne succeeds — user now has trial extended.
  2. MarkProcessed fails (Mongo blip, context deadline).
  3. Next 1s poll picks up the same row again.
  4. Re-reads user, sees the extended expiry, treats it as the "existing" base.
  5. Adds another 3 days on top — the user just got 6 days for one purchase.
The transaction collapses that window: either both writes commit (and the row never re-enters the queue) or neither writes (and the next poll starts fresh).

Edge case — user deleted between purchase and consumption: If the user document is gone, mark the row processed (with a sentinel return) so we don't spin retrying. Log it for operator visibility.

Why this order? Cheap checks first. muted is a set membership (O(1), no Redis). quietHours is local arithmetic. Both fail fast without touching Redis. Only allowed-so-far events spend Redis ops on dedup + cap.

Quiet hours in user's local timezone — we store the user's timezone (default IST) on their profile so a user in California gets quiet hours at their 11pm, not India's. The check resolves IST 23:00 → local 23:00 by using the stored tz offset.

Dedup TTL = 1 hour, not 5 minutes. If the system tries to send two "streak warning" pushes 30 minutes apart, the second is dropped. Prevents notification spam from a buggy upstream producer.

Daily cap = 10. Soft cap — the counter is incremented before the comparison, so during a burst the 11th notif gets through and the 12th gets dropped (concurrency race). Acceptable.

pkg/coins/ledger.go — the transactional grant

func (l *Ledger) Grant(ctx context.Context, userID string, delta int64,
                       reason, refID string, metadata map[string]string) (*LedgerEntry, error) {
    // Fast path: if a matching entry already exists, return it without opening
    // a transaction. The unique index on (userId, refId, reason) is the truth.
    if existing, err := l.findExisting(ctx, userID, refID, reason); err != nil {
        return nil, err
    } else if existing != nil {
        return existing, nil                  // ⬅ idempotent replay
    }

    // Slow path: open a Mongo session and run the grant in a transaction.
    session, _ := l.client.StartSession()
    defer session.EndSession(ctx)

    result, err := session.WithTransaction(ctx, func(sc context.Context) (any, error) {
        return l.GrantInSession(sc, userID, delta, reason, refID, metadata)
    })
    // GrantInSession does:
    //   1. InsertOne(coin_ledger, { userId, delta, reason, refId, balance_after, ... })
    //   2. UpdateOne(users, { $inc: { coins: delta } })
    //   3. If the InsertOne fails with DuplicateKey, re-read the existing entry
    //      and return it as success (concurrent caller won the race).
}

Why a fast path? Opening a Mongo session and starting a transaction costs ~5-10ms even for read-only work. Most "duplicate" calls (retries from a flaky network) can be answered with a single indexed read.

The unique index on (userId, refId, reason) is the actual idempotency guarantee. Even if two goroutines race past the fast-path check (both find nothing), only one Insert wins; the other gets DuplicateKey, re-reads, returns the winner's entry. No double-grant possible.

pkg/ratelimit — fixed-window with Redis

func (l *Limiter) Allow(ctx context.Context, subject string) (bool, error) {
    windowStart := time.Now().UnixNano() / l.window.Nanoseconds()
    //             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //             integer division → the same value for an entire window
    key := fmt.Sprintf("ratelimit:%s:%s:%d", l.name, subject, windowStart)

    pipe := l.rdb.TxPipeline()
    incr := pipe.Incr(ctx, key)
    pipe.ExpireNX(ctx, key, l.window+time.Second)   // safety margin so key
                                                    // outlives the window
    if _, err := pipe.Exec(ctx); err != nil {
        return true, err                            // ⬅ fail OPEN
    }
    return incr.Val() <= int64(l.limit), nil
}

How it works: Compute which "bucket" we're in by integer-dividing the current nanoseconds by the window size. Every call in the same bucket shares a Redis key. INCR increments a counter; if it exceeds the limit, deny.

Why ExpireNX? Only set the expiry if it isn't set yet. Otherwise every call would extend the TTL, defeating the bucket boundary.

Why fail-open on Redis errors? Rate-limiting is a soft guard, not a security boundary. If Redis is down, the user should still be able to log in.

pkg/auth — the JWT generator (full source)

const TokenTTL = 24 * time.Hour

type Claims struct {
    UserID   string `json:"sub"`
    Username string `json:"username"`
    jwt.RegisteredClaims
}

func GenerateToken(userID, username, secret string) (string, error) {
    claims := Claims{
        UserID:   userID,
        Username: username,
        RegisteredClaims: jwt.RegisteredClaims{
            Subject:   userID,                                  // standard "sub" claim
            ExpiresAt: jwt.NewNumericDate(time.Now().Add(TokenTTL)),
            IssuedAt:  jwt.NewNumericDate(time.Now()),
        },
    }
    token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
    return token.SignedString([]byte(secret))
}

func VerifyToken(tokenStr, secret string) (*Claims, error) {
    token, err := jwt.ParseWithClaims(tokenStr, &Claims{}, func(t *jwt.Token) (interface{}, error) {
        if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
            return nil, errors.New("unexpected signing method")   // ⬅ blocks alg:none
        }
        return []byte(secret), nil
    })
    if err != nil { return nil, err }
    return token.Claims.(*Claims), nil
}

The alg:none guard is the line every JWT tutorial forgets and every JWT CVE exploits. Without it, an attacker can craft a token with header {"alg":"none"} and an unsigned payload; some JWT libraries would accept it. By explicitly type-asserting *jwt.SigningMethodHMAC, we refuse anything but HS256/384/512.

Cross-cutting Patterns

The Outbox Pattern

Problem: Service A debits coins from a user (Mongo write) and also needs service B to extend their premium plan. If A writes to Mongo and then publishes to RabbitMQ but crashes between the two, the coin is debited and nothing happens — money lost to the user.

Solution: Write the "I owe you this effect" record to a Mongo collection (coin_effect_outbox) in the same transaction as the coin debit. A background poller in service B reads unprocessed rows, applies the effect, marks them processed. Crash-safe by construction — the row is durably stored before anyone acks.

┌─────────────────────────────────┐ │ SCORING (one Mongo txn) │ │ ─────────────────────── │ │ coin_ledger.insert(-99) │ │ users.coins -= 99 │ │ outbox.insert(kind="premium")─┼─┐ │ │ │ └─────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────┐ │ PAYMENT (background poller, 1s tick) │ │ ──────────────────────────────────── │ │ for row in outbox.where(!processed): │ │ users.planExpiresAt += 3d │ │ row.processed = true (same txn) │ └─────────────────────────────────────────┘

See ADR-0003 for the full reasoning. Used twice in this codebase: (1) premium-trial coin shop item, (2) friend-challenge notification.

The two outbox collections

CollectionPurposeProducerDrainerTick
coin_effect_outboxPremium trials from shopscoring (PurchaseShopItem)payment1s

Why two different tick intervals?

Premium trial = 1s. User just spent coins. They expect "Premium activated" within seconds. Tight poll = instant-feeling UX.

Friend challenge = 30s. The notif is the safety net for a failed Rabbit publish (which is the rare path). The normal path is publish-inline-and-mark-processed-immediately, before the drain tick ever sees the row. The 30s ticker exists to clean up rows that got stuck during a transient broker outage.

The transactional bond — what makes outbox crash-safe

The producer's main effect and the outbox row must commit together. In Mongo:

session.WithTransaction(ctx, func(sc context.Context) (any, error) {
    // (A) main effect: debit coins
    ledger.GrantInSession(sc, userID, -99, "shop_purchase", refID, ...)

    // (B) outbox row: record the side-effect we owe
    db.Collection("coin_effect_outbox").InsertOne(sc, OutboxRow{
        UserID: userID, Kind: "premium_trial",
        Payload: map[string]string{"days": "3"},
    })

    return nil, nil   // commit both, or roll back both
})

Either the user's coins went down AND a pending row exists in the outbox, or neither happened. There is no state where coins are debited but the outbox is empty (which would mean: user lost coins, never gets premium). MongoDB transactions on a replica set (we run rs0 single-node) guarantee this atomicity.

The drainer's transactional bond

And on the consumer side, the apply-effect and the mark-processed must commit together:

session.WithTransaction(ctx, func(sc context.Context) (any, error) {
    // (C) apply effect: extend planExpiresAt
    users.UpdateOne(sc, {_id: userID}, {$set: {plan: "premium", planExpiresAt: expiry}})

    // (D) mark outbox row processed
    outbox.UpdateOne(sc, {_id: rowID}, {$set: {processedAt: now}})

    return nil, nil
})

Without this, a crash between C and D would leave the user with extended premium AND an unprocessed row — next 1s poll would re-extend, granting double the days. (Exactly the bug ADR-0003 was written to prevent.)

Idempotency — the four flavors used in this codebase

Doing the same thing twice should equal doing it once. Critical when: (a) clients retry on network errors, (b) consumers redeliver after a crash, (c) payment gateways send duplicate webhooks, (d) outbox drainers re-publish after a crash mid-mark-processed.

Flavor 1: SETNX with rollback (single-attempt-wins)

ok, _ := rdb.SetNX(ctx, "payment:idem:"+paymentID, "in_progress", time.Hour).Result()
if !ok {
    // Someone else got there first. Return their result by re-reading state.
    return s.GetPlanStatus(...)
}
defer func() {
    if err != nil { rdb.Del(ctx, "payment:idem:"+paymentID) }   // rollback on failure
}()
// ... do the actual work ...

Used by: VerifyPayment, Razorpay webhook, challenge throttle, notification dedup.
Win condition: the first SETNX to return true.
TTL on the key: bounded — if we crash, retries can succeed once the TTL expires (1 hour for payment, 30s for challenge throttle, 1 hr for notif dedup).
Rollback on error: mandatory. Otherwise a transient error during the actual work would lock retries out until the TTL expires.

Flavor 2: Unique Mongo index (any-attempt-wins, dedup by content)

// Index defined in seed:
db.coin_ledger.createIndex({ userId: 1, refId: 1, reason: 1 }, { unique: true })

// In code:
_, err := coll.InsertOne(ctx, entry)
if mongo.IsDuplicateKeyError(err) {
    // Another goroutine wrote this exact (userId, refId, reason) tuple.
    // Re-read the winner's row and return it.
    return findExisting(ctx, userID, refID, reason)
}

Used by: coin_ledger grants, friend_requests, payments collection.
Win condition: first InsertOne to commit. Losing inserts get DuplicateKeyError; the application re-reads the winner's row.
Why not SETNX? The "key" we want to dedup on is multi-field and lives in Mongo anyway. A unique index makes Mongo itself the dedup authority — no second moving part.

Flavor 3: Idempotent upsert (UpdateOne with $set)

// EquipCosmetic: equipping an item the user already has equipped is a no-op,
// not an error. UpdateOne with the same payload is idempotent at the Mongo level —
// the second call writes the same value, no extra effect.
_, _ = coll.UpdateOne(ctx,
    bson.M{"userId": userID, "category": "avatar"},
    bson.M{"$set": bson.M{"itemId": itemID, "equippedAt": time.Now()}},
    options.Update().SetUpsert(true),
)

Used by: equipping cosmetics, updating FCM token, profile updates.
When it's enough: the target state is fully determined by the request — no counters, no append-only logs.

Flavor 4: refID as the idempotency anchor (re-read existing)

// Lattest, the Grant function checks for an existing entry BEFORE opening a
// transaction. Saves ~5-10ms on retries:
if existing, _ := l.findExisting(ctx, userID, refID, reason); existing != nil {
    return existing, nil      // idempotent replay — return the original entry
}

Caller passes a refID ("the thing that caused this grant"). Examples:

  • Daily reward → refID = "streak:2026-05-12" (the date)
  • Match win → refID = the match ID
  • Referral → refID = the referral document ID
  • Shop purchase → refID = "purchase:<itemID>:<idempotencyKey>"
Multiple grants for the same logical event share a refID, dedupe naturally.

The mental model

Idempotency is not "one mechanism." It's a property — "calling this twice equals calling it once" — implemented differently depending on what you're protecting:
• Single-flight in-flight gates → SETNX (with TTL + rollback).
• Append-only event records → unique index on the "what caused this" tuple.
• Idempotent state writes → UpdateOne with full $set.
• Application-level dedup → refID convention + fast-path read.

Graceful Shutdown

Kubernetes (or Docker, or you hitting Ctrl-C) sends SIGTERM. A naïve server exits immediately and drops in-flight RPCs. We do this instead:

ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer stop()

// ... boot service, start consumers (all observe ctx) ...

<-ctx.Done()                  // wait for signal

grpcServer.GracefulStop()      // drain in-flight RPCs, refuse new ones
metricsServer.Shutdown(timeoutCtx)
amqpChannel.Close()
mongoClient.Disconnect(ctx)

All background goroutines (cron tickers, AMQP consumers) select on <-ctx.Done() and exit themselves. See PR-C1.

Protects critical endpoints from abuse and DoS. Algorithm: Redis INCR + EXPIRE on first hit. If the counter exceeds the limit before TTL, reject.

Redis Lua scripts

Redis runs Lua atomically — no other command can interleave. We use one script: the live-leaderboard update.

Why: Two players answer simultaneously. Without atomicity, both Go goroutines might ZSCORE the same starting value, add their respective deltas, and ZADD — losing one update. Lua makes the read-add-write a single atomic op.

gRPC Server Streams

Two RPCs hold long-lived server-to-client streams:

  • SubscribeToMatch — Flutter calls it after JoinMatchmaking, the server holds the stream open until a match is created (could be seconds), then pushes one event and closes.
  • StreamGameEvents — runs for the duration of a match (~2-3 min). Pushes question broadcasts, leaderboard updates, round results, timer syncs.

The alternative would be client polling — far more network/server load. Streams are basically HTTP/2 long-poll with type safety.

Key Flows — Step by Step

Login flow

  1. Flutter auth_service.dart calls AuthService.Login(username, password) over gRPC.
  2. Auth service rate-limits 5/min/username, looks up the user in Mongo, bcrypt-compares the hash.
  3. On success, generates a JWT (HS256, 24h exp, claims = {userId, username}) and returns it.
  4. Flutter stores the token in shared_preferences, attaches it as Authorization: Bearer ... metadata on every subsequent gRPC call.
  5. Other services' interceptors verify the JWT and put the user ID in the request context — handlers never re-parse it.

Match lifecycle (the full ~3 minutes)

  1. Player taps Play → Flutter calls Matchmaking.JoinMatchmaking (gRPC). Quota check, ZADD pool. Then opens SubscribeToMatch stream and waits.
  2. Matchmaking pairer goroutine pairs two players in the rating window, removes them from the pool, generates a room ID, writes room:{id}:players hash to Redis, publishes match.created to RabbitMQ.
  3. The pairer pushes a MatchEvent with room_id + opponent down both SubscribeToMatch streams and closes them.
  4. Flutter receives the event, navigates to the gameplay screen, opens two new RPCs: GetRoomQuestions (one-shot) and StreamGameEvents (long-lived).
  5. Quiz service consumes match.created from RabbitMQ, loads 10 questions from Mongo, primes the room state in Redis, schedules a QuestionBroadcast + a deadline timer for round 1.
  6. Quiz pushes QuestionBroadcast to both streams. Players answer via SubmitAnswer. Quiz publishes game.answer; scoring consumes, calls CalculateScore loopback, Lua-updates the leaderboard ZSET, pushes a LeaderboardUpdate event back through the quiz stream.
  7. Deadline hits (or both players answered) → Quiz pushes RoundResult (correct answer revealed), increments the round, loops to step 6 until 10 rounds done.
  8. Quiz publishes match.finished to RabbitMQ. Scoring consumes: persists to answer_log, rating_history, calls coins.Ledger.Grant(matchWinCoinReward=100, reason="match.win") for the winner.
  9. Quiz pushes MatchEnd down the stream, closes it. Flutter navigates to results screen.

Coin-grant lifecycle

  1. Some event triggers a grant — match win, referral conversion, daily reward, shop refund.
  2. Service calls coins.Ledger.Grant(userId, delta, reason, refId).
  3. Ledger opens a Mongo transaction:
    • Insert row in coin_ledger (delta, reason, refId, balance_after, metadata, timestamp).
    • $inc users.coins by delta.
    Commit. If the (userId, refId, reason) unique index is violated → grant was already applied → return idempotent success.
  4. Optionally publishes coin.earn.{reason} to RabbitMQ for downstream notifications.

Read flows (GetCoinBalance, GetCoinLedger with keyset pagination) reuse the same package.

Payment flow

  1. Flutter calls Payment.CreateOrder(plan=monthly).
  2. Backend calls Razorpay Orders API server-side (needs key_secret), stores row in payments (status=created), returns (order_id, key_id, amount, currency) to Flutter.
  3. Flutter opens Razorpay native Checkout SDK with those values. User pays (UPI / card).
  4. On capture, Razorpay returns (razorpay_payment_id, razorpay_order_id, razorpay_signature) to the Flutter callback.
  5. Flutter calls Payment.VerifyPayment(...). Backend:
    • SETNX payment:idem:{paymentId} with 1-hour TTL. First caller proceeds; concurrent retries get an idempotent no-op.
    • Verify HMAC_SHA256(order_id + "|" + payment_id, key_secret) == signature.
    • Mongo update: plan="premium", planExpiresAt=now+30d.
    • Publish notif.premium.activated.
    • On any failure: DEL payment:idem:{paymentId} so retry can succeed.
  6. Razorpay also calls our POST /webhook server-to-server (~1-2s later). Same HMAC verify + SETNX dedup; if VerifyPayment already ran, webhook is a no-op.

Friend challenge (the new feature from commit 8b5e952)

  1. Alice taps "Challenge" on Bob in friends_screen.dart.
  2. Flutter calls Scoring.ChallengeFriend(targetUserId=Bob).
  3. Scoring validates an accepted friendship exists (either direction); SETNX challenge:throttle:{alice}:{bob} for 30s to debounce rapid taps.
  4. Creates a room ID, writes room:{id}:players hash to Redis with both users (same format as a pool-matched room — quiz can't tell the difference).
  5. Publishes match.created → quiz prepares the room.
  6. Inserts a row in coin_effect_outbox with kind="challenge_notif", payload={fromAlice, toBob, roomId}. This is the durability guarantee: even if scoring crashes here, the row is in Mongo.
  7. Returns room_id to Alice's Flutter; she navigates to matchmaking screen and the existing SubscribeToMatch flow picks up the match.
  8. Scoring's drainChallengeNotifOutbox goroutine picks up the outbox row → publishes notif.friend.challenge to RabbitMQ → marks row processed.
  9. Notification service consumes notif.friend.challenge → policy gate (quiet hours, mute) → sends FCM to Bob's phone.
  10. Bob taps the notification → Flutter's _handleFcmTap in main.dart recognizes notif.friend.challenge, navigates Bob into matchmaking which auto-joins the same room.

The flow of a single screen

  1. Widget calls ref.watch(somethingProvider).
  2. Provider's body invokes a service (e.g. FriendsService.getFriendsList()).
  3. Service wraps the generated gRPC stub, attaches the JWT in metadata, returns typed results.
  4. Widget rebuilds with the data.
  5. On user action (Challenge tap, Accept tap), widget calls a service method and (on success) ref.invalidate(somethingProvider) to force a refetch.

State management — Riverpod patterns we use

  • Provider — for singletons (service instances, shared gRPC channels).
  • FutureProvider — for one-shot async data (friends list, coin balance, leaderboard).
  • StreamProvider — for gRPC server-streaming subscriptions.
  • NotifierProvider — for stateful logic the user mutates (the in-match GameNotifier).
  • Derived providers — e.g. friendRequestsCountProvider computes a badge count from friendRequestsProvider without a separate fetch.

Why four channels and not one? Each gRPC service runs on a different port. gRPC channels are 1:1 with TCP connections, so we need one per host:port.

Why ChannelCredentials.insecure()? Local dev only — no TLS. Production would use ChannelCredentials.secure() with a root cert. The backend doesn't currently terminate TLS itself; that'd be a load balancer's job.

Presence — the heartbeat in detail

Server side (pkg/keys/redis.go:407):

const PresenceTTL = 60 * time.Second        // ⬅ 60s, not 5min as earlier draft said

func TouchPresence(ctx context.Context, rdb *redis.Client, userID string) error {
    return rdb.Set(ctx, Presence(userID), "1", PresenceTTL).Err()
}
// Key:   presence:<userID>
// Value: "1"  (we only ever check existence)
// TTL:   60s — refreshed on every Heartbeat RPC

Flutter side (sketch from main.dart):

Timer? _presenceTimer;

void _startPresenceHeartbeat() {
    _firePresence();                                        // once immediately
    _presenceTimer = Timer.periodic(Duration(seconds: 30), (_) {
        _firePresence();
    });
}

@override
void didChangeAppLifecycleState(AppLifecycleState state) {
    if (state == AppLifecycleState.paused) {
        _presenceTimer?.cancel();                           // app backgrounded — stop pings
    } else if (state == AppLifecycleState.resumed) {
        _startPresenceHeartbeat();                          // immediate fire on resume
    }
}

Why TTL = 2× the ticker interval? One dropped heartbeat (transient network blip) wouldn't flip the user offline. Two consecutive misses do. Trade-off: a crashed app shows online for up to 60 seconds, but no flicker for healthy clients.

Why immediate fire on resume? User opens the app, the friends screen renders within 100ms. If we waited 30 seconds for the next periodic tick, friends would see them offline for half a minute after they're clearly back.

The challenge outbox — durability story

The actual row shape (services/scoring/friends_outbox.go:39):

type challengeNotifOutboxRow struct {
    ID           string     `bson:"_id"`
    RecipientID  string     `bson:"recipientUserId"`
    FromUserID   string     `bson:"fromUserId"`
    FromUsername string     `bson:"fromUsername"`     // denormalized so notif copy
                                                       // doesn't need a users lookup
    RoomID       string     `bson:"roomId"`
    Attempts     int        `bson:"attempts"`         // bumped on republish failure
    CreatedAt    time.Time  `bson:"createdAt"`
    ProcessedAt  *time.Time `bson:"processedAt,omitempty"`   // nil = pending
}

Collection: friend_challenge_outbox. Drainer interval: 30 seconds. Batch size: 200 rows. First pass runs immediately on service boot — so a service that crashed mid-publish 10 seconds ago doesn't make the user wait 30s for first retry.

Why this needs an outbox at all: A friend challenge is a two-effect operation: create a room (Redis write) AND push a notification (RabbitMQ publish → notification service → FCM). Naïve order-of-operations risks:

  • Publish first, room-create fails → recipient gets a notification for a non-existent challenge.
  • Room-create first, publish fails → challenger thinks they're in a game, recipient never knows.

The outbox solves both: Room is created inline (synchronous, the room ID is needed in the response). The notif is enqueued as a Mongo row — durable. The drainer publishes it asynchronously and marks the row processed on success. If publishing fails, the row sits in the queue. If the service crashes between publish and mark-processed, the next drain pass publishes again — the notification service is idempotent on (recipientId, roomId), so duplicates just buzz the phone twice.

CI — GitHub Actions, line by line

One workflow file, two jobs, runs on every push and PR against dev and main. The whole thing lives at .github/workflows/ci.yml and is ~56 lines. Recent history: 49/50 runs green over the last 50 attempts (the one failure was a missed gofmt column-alignment in PR #54 — caught and fixed in the same hour).

What CI is actually proving

That every Go service compiles, vets clean, is gofmt-clean, and its tests pass against a real Mongo replica set. That the Flutter app analyzes clean and its tests pass. Nothing else — no Docker image build, no integration tests, no security scanning, no deploy. The audit in docs/production-readiness.md calls these out as gaps; CI today is a "does the code build and behave at the unit level" gate, not a release pipeline.

The trigger model

on:
  pull_request:
    branches: [dev, main]
  push:
    branches: [dev, main]

Two triggers, both for the same protected branches:

  • pull_request — fires when a PR is opened, synced (new commit pushed), or reopened. This is what blocks merges: the branch-protection rule on dev/main requires a green ci check before the Merge button lights up.
  • push — fires when commits land directly on dev or main (i.e. after merge). Re-runs the same job set against the freshly-merged state. Catches the rare case where a merge between two green PRs produces a broken combination — the post-merge run is what would surface it, and reviewers can revert quickly.

Not triggered on: feature branches (no push against feature/*), tags, schedule, or manual dispatch. Tag-based release builds and nightly schedules are future work.

Job 1 — go

The biggest job, ~30 lines because of the inline Mongo setup. Runs on ubuntu-latest.

Step 1: checkout + Go toolchain

- uses: actions/checkout@v4
- uses: actions/setup-go@v5
  with: { go-version: '1.25' }

Stock actions. Pinned to v4 / v5 (major pins) rather than digest pins — Renovate / Dependabot would normally bump these. Go is pinned to 1.25, matching go.mod and the Dockerfile's build stage. A patch upgrade (1.25.x → 1.25.y) floats; a minor bump is intentional and requires editing this line in lock-step with go.mod.

Step 2: start Mongo as a single-node replica set

- name: Start Mongo rs0
  run: |
    docker run -d --name mongo -p 27017:27017 mongo:6 --replSet rs0 --bind_ip_all
    ready=false
    for i in $(seq 1 30); do
      if docker exec mongo mongosh --quiet \
           --eval 'db.runCommand({ping:1}).ok' | grep -q '^1$'; then
        ready=true; break
      fi
      sleep 2
    done
    [ "$ready" = "true" ] || {
      echo "mongod never accepted connections" >&2
      docker logs mongo >&2 || true
      exit 1
    }
    docker exec mongo mongosh --quiet \
      --eval 'rs.initiate({_id:"rs0",members:[{_id:0,host:"localhost:27017"}]})'
    primary=false
    for i in $(seq 1 30); do
      if docker exec mongo mongosh --quiet \
           --eval 'db.hello().isWritablePrimary' | grep -q '^true$'; then
        primary=true; break
      fi
      sleep 2
    done
    [ "$primary" = "true" ] || {
      echo "rs0 never reached PRIMARY" >&2
      docker logs mongo >&2 || true
      exit 1
    }
Why this is hand-rolled, not services: mongo: ...

GitHub Actions does have a built-in services block for sidecar containers like Mongo. We can't use it here because services.<id>.options only forwards docker create flags — there's no way to pass --replSet rs0 (a mongod CMD argument) through that block. And we need a replica set: pkg/coins/ledger.go uses Mongo multi-document transactions, which a standalone Mongo doesn't support. So we shell out to docker run explicitly. The comment in ci.yml documents this so nobody "simplifies" it back to services: and breaks every ledger test.

What the readiness loop does:

  1. Phase 1 — TCP/auth ready. Loops up to 30 × 2s = 60 seconds, polling db.runCommand({ping:1}).ok. This catches the cold-start window where the container is up but mongod hasn't bound the port yet.
  2. rs.initiate. One-shot. Idempotent only if the container is fresh — re-running on an existing replica set returns an error, but we never do that in CI (each job gets a fresh container).
  3. Phase 2 — PRIMARY elected. Another 60-second poll for db.hello().isWritablePrimary. Single-node replica sets still elect a primary (themselves), but the election takes a beat — race the next step and writes fail with NotWritablePrimary.
  4. Failure path. If either phase times out, dump docker logs mongo to stderr so an operator can diagnose the regression — was it network? OOM? init failure?

Step 3: Go test pipeline

- run: go mod download
- run: make vet
- run: make lint
- run: make test
  env:
    MONGO_URI: mongodb://localhost:27017/?replicaSet=rs0&directConnection=true

Three Makefile targets, run in sequence. The first failure stops the job — fast-fail intentionally so CI burns 5 seconds on a format mistake instead of 5 minutes on the full test run.

TargetWhat it runsWhy before tests
make vetgo vet ./...Catches obviously wrong Go (printf-format mismatches, unreachable code, struct-tag typos). Free; takes ~1s.

The lint target's flutter exclusion

gofmt -l . | grep -v '^flutter/' — the pipe filters out anything under flutter/ so Dart files don't make gofmt trip. Without it, gofmt would crawl the Dart codebase, find nothing to format, and report no issues — but it'd scan thousands of files unnecessarily. The exclusion is purely a performance hint plus a guard against a future gofmt version misclassifying a Dart string.

Job 2 — flutter

flutter:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: subosito/flutter-action@v2
      with: { flutter-version: '3.41.x', channel: stable }

Much simpler — no infrastructure to spin up because Flutter tests run against in-memory fakes (no Mongo / Redis / Rabbit dependency).

  • subosito/flutter-action@v2 — third-party action that installs the Flutter SDK on the runner. Pinned to 3.41.x (matches our pubspec.yaml's environment.flutter). Stable channel; beta would introduce non-reproducible builds.
  • flutter pub get — resolves dependencies from pubspec.lock. No version drift because the lock file is committed (and updated when we add a dep like flutter_secure_storage).
  • flutter analyze --no-fatal-warnings — runs the Dart analyzer using analysis_options.yaml. --no-fatal-warnings means warnings don't fail the build (only errors do). Worth re-evaluating — the file has intentional warnings we don't want regressing.
  • flutter test — runs every *_test.dart under flutter/test/. ~12 test files at last count; covers screen state machines, service wrappers, and a few widget unit tests.

What runs in parallel vs. in series

The two jobs (go and flutter) run in parallel — they don't needs: each other. Total wall-clock is whichever is slower. Typical timings from recent runs:

  • go: ~1m 30s (Mongo cold-start dominates ~30s; tests are ~50s)
  • flutter: ~2m 0s (Flutter SDK install dominates ~80s; analyze + test ~30s)

So a typical PR check takes ~2 minutes end-to-end. The branch- protection rule requires both jobs green before merge.

How the workflow handles a typical PR lifecycle

  1. You push to a feature branch. Nothing happens — CI doesn't watch feature branches.
  2. You open a PR against dev. Both jobs start in parallel. ~2 minutes later, two checkmarks (or two ❌s).
  3. You push a fix. Both jobs cancel the previous run? No — we don't have concurrency.group configured. Two concurrent runs happen, both eventually finish. The newer one's result is what's shown on the PR.
  4. PR merges to dev. The push trigger fires the same two jobs against the post-merge state. Catches the rare conflict-merge regression.
  5. Branch is deleted. No cleanup action — no caches to invalidate.

Debugging a CI failure

From the local terminal:

# List recent runs
gh run list --limit 10

# Watch a specific run live
gh run watch <run-id>

# Pull the failed job's log
gh run view <run-id> --log-failed --job <job-id>

# Re-run only the failed jobs (after pushing a fix)
gh run rerun <run-id> --failed

The PR #54 failure was diagnosed exactly this way: gh pr checks 54 showed go: fail; gh run view --log-failed surfaced gofmt needed in: pkg/validate/validate_test.go; gofmt -d locally showed the missing-space alignment; gofmt -w fixed it; push triggered a re-run; green in 1m36s.

Fresher note

If you're new to GitHub Actions: a workflow is a YAML file under .github/workflows/. It contains one or more jobs, each running on a fresh VM (runner) that GitHub provisions. Inside a job, steps run sequentially. Jobs run in parallel by default unless you wire needs: dependencies. The whole thing is event-driven — the on: block at the top declares what triggers the workflow.
